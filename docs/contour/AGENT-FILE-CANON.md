# AGENT-FILE-CANON — канон файловой модели агента

**Статус:** v1 (Ram×RAM, 17.11.2026). Единое описание того, из каких файлов
состоит агент ZeroClaw, за что каждый отвечает, кто и как его правит и как
это всё попадает в контекст. Написано, чтобы не потерялось: апстрим такого
концептуального описания не имеет (в апстриме personality-файлы —
несколько необязательных md-файлов в воркспейсе без разделения ролей).

  (список файлов — `PERSONALITY_FILES`, потолок 20 000 симв. на файл —
  `MAX_FILE_CHARS`, строки 8–24).
- Шаблон: `C:/Users/Homework/.zeroclaw/agents/_template/` (7 файлов + wiki/).
- Канон порождения: `C:/Users/Homework/.zeroclaw/agents-canon.toml`
  (template.base v2, риск-/рантайм-профили, крон-промпты).
- Концепт памяти: `AGENT-MEMORY-CONCEPT.md` v0.5 (слой L0.5 «Ось», Д0).
- Инженерия шаблона: `_maintenance/agent-template-design.md` (локальный,
  в gitignore — суть перенесена сюда, §7–8); provisioner и drift-check —
  `C:/Users/Homework/.zeroclaw/service/`.

## 1. Принципы (держат всю модель)

1. **Материализация, не наследование.** Порождение агента = рендер шаблона
   в обычные файлы и структуры ZeroClaw. После рендера агент самодостаточен;
   рантайм про шаблон не знает. Шаблон меняется — уже живые агенты не меняются
   (их дрейф ловит drift-контроль по origin_marker, не автосинк).
2. **Один факт — одно место.** Каждый факт о себе агент хранится ровно в одном
   файле; остальные файлы либо не дублируют его, либо содержат явно помеченную
   производную (дистиллят с маркером `<!-- NARRATIVE:... -->`).
3. **Резидентность решает цена контекста.** В системный промпт грузится только
   то, что нужно на каждом ходу. Всё процедурное живёт вне промпта и
   подгружается по требованию (скиллы, wiki, файлы сессий).
4. **Вся долговременная правка — через маркер или протокол.** Агент не
   переписывает канонические файлы целиком: дописка — через маркер
   (`APPEND_MEMORY_BELOW`, `APPEND_IMAGE_BELOW`), правка канона — через
   предложение оператору. Это защита и от дрейфа, и от случайной порчи.
5. **Кто правит — определено для каждого файла** (матрица в §5). Самоизменение
   агента разрешено и поощряется, но привязано к оси (Д0, см. §6).

## 3. Каждый файл: роль, наполнение, правила правки

### IDENTITY.md — ось (миссия)
- **Что:** кто агент, какая его роль, хозяева контура, статус, **генезис**
  (создан, заявка, решение, поручение). С v0.5 концепта — это **ось**:
  «то, чем агент должен стать», нулевой слой памяти, держатель идентичности
  против дрейфа.
- **Кто правит:** создатель/владелец агента. Агент — read-only; противоречие
  миссии наблюдением оформляется proposal'ом на пересмотр оси (9-4).
- **Особенность:** самый медленный файл контура. Правки — только новой версией
  с changelog. Версионируется git'ом (ритуал self-review коммитит воркспейс).

### SOUL.md — ядро характера (регулятор)
- **Что:** неизменное ядро поведения: тон, стоп-правила, трассировка
  («ни одного утверждения без основания»), маркировка неопределённости,
  честные ограничения. Плюс служебные роли («Хранитель образа» у legalplat).
- **Кто правит:** владелец контура. Агент в своём само-ревью прямо запрещен
  его трогать («SOUL.md и IDENTITY.md не трогать — только владелец/отец»).
- **Особенность:** сюда же (у legalplat) DEPLOY-синком пишется дистиллят
  образа в разделе `<!-- NARRATIVE:BEGIN/END -->` — это производная из
  brain.db, не источник истины.

### USER.md — оператор и вызывающие
- **Что:** кто владелец (Ram, chat_id), кто ревьюер, кто имеет право звать.
- **Кто правит:** владелец контура при порождении; дальше — только он.

### AGENTS.md — рабочий регламент + доменная дельта
- **Что:** базовый цикл работы («понять → уточнить → выполнить → проверить →
  отчёт»), ссылки на скиллы-процедуры, доменный раздел. У legalplat — также
  операционные протоколы: дельта образа в `image-pending.md`, правило
  «относительные пути от workspace», запрет на составные shell-команды.
- **Кто правит:** агент — **инкрементально, одно правило = одна точечная
  правка**, в ходе еженедельного self-review. Доменную дельту при порождении
  задаёт провижионер (`--domain-file`).
- **Ограничение:** процедура длиннее ~25 строк не живёт здесь — только скилл
  + строка-триггер. Источник истины регламента — файл скилла, не пересказ.

### TOOLS.md — инструментальная матрица
- **Что:** какие инструменты разрешены и с какими рамками, общие скрипты
  контура (docgen), правило обработки ошибки инструмента (другой путь или
  эскалация; ретрай тем же аргументом запрещён).
- **Кто правит:** владелец контура; агент дописывает найденные инструментальные
  уроки инкрементально.

### HEARTBEAT.md — контекст пробуждений
- **Что:** персональные правила для крон-прогонов (что проверять при
  «сердцебиении»). В шаблоне пустой — заполняется при порождении, если агенту
  нужны периодические прогоны.
- **В промпт попадает** только в крон-прогонах; в изолированных/ACP-режимах
  файлы personality грузятся без него по общему списку
  (`personality.rs`: изоляция исключает MEMORY.md, остальные шесть — всегда).

### MEMORY.md — уроки (быстрая память выводов)
- **Что:** уроки одной строкой в формате `§ ДАТА | категория | источник |
  правило | триггер` (категории dialog|tool|infra|method|format; источник
  manual|correction|auto). **Единственная точка дописки — маркер
  `APPEND_MEMORY_BELOW`.**
- **Бюджет:** ≤ 6000 байт. Бюджет — не ограничение, а механизм отбора
  (урок Гермеса: его MEMORY.md на 99% заполнен, и это лучшее, что с ним
  случилось). Превышение — только со слиянием дублей и устаревшего,
  размер до/после в отчёт.
- **Кто правит:** агент, в регламенте еженедельного self-review
  (свип auto-уроков: подтверждённые → manual, отвергнутые удалить с отметкой).

### wiki/ — медленная память знаний
- **Что:** курируемые знания: понятия, сущности, сравнения, ответы на
  повторяющиеся вопросы. Очереди на разбор в `_staging/`
  (`pending.md` — знания, `image-pending.md` — дельты образа).
- **В промпт НЕ попадает** — только через `file_read`. Компиляция —
  еженедельный крон (lint → разбор staging → index/log → git-коммит).
- **Кто правит:** агент по регламенту скилла llm-wiki; канон (страницы
  образа) — только через утверждение оператором.

## 4. Механика попадания в контекст (по коду)

1. Каждый ход рантайм читает `PERSONALITY_FILES` из воркспейса
   (`personality.rs:8–24`): **SOUL, IDENTITY, USER, AGENTS, TOOLS, HEARTBEAT,
   MEMORY** — в этом порядке.
2. Потолок — **20 000 символов на файл**. Превышение не роняет загрузку:
   файл обрезается, в промпт идёт пометка
   `[... <файл> truncated at 20000 chars — use `read <файл>` for full file]`.
   То что переполненный файл «просто работает» — ловушка: вся «хвостовая»
   часть молча невидима. Контроль размеров — часть self-review.
3. Изолированный/ACP-режим: MEMORY.md исключается, шесть остальных грузятся
   (плюс внутренний default, если файла нет на диске).
4. Итого резидентная часть промпта: ≤ 7 файлов × 20k ≈ **до 140k символов
   теоретического потолка**, реально в шаблоне ~9k суммарно. Над этим —
   системный промпт рантайма, история (см. §5) и инжект памяти (recall).

## 5. Экономия контекста: три кольца резидентности

| Кольцо | Что | Как попадает | Потолок |
|---|---|---|---|
| Всегда | 7 personality-файлов | personality.rs, каждый ход | 20k/файл |
| По требованию | скиллы (read_skill), wiki (file_read), сессии, документы | агент сам подгружает, когда триггер совпал | бюджет итераций рантайма |
| Никогда напрямую | сырьё (raw/), архивы транскриптов, чужие воркспейсы | только через поиск/дайджест | — |

История диалога — отдельный бюджет (runtime-профиль `worker_base`):
`compact_context = true`, `max_history_messages = 30`, нижний потолок
тримминга целыми ходами `history_pruning.max_tokens = 57344`,
`prompt_injection_mode = "compact"`. Компактификация теряет дословность —
страховка от этого: файлы выше (резидентные + wiki + сессии живут вне
истории и compaction их не трогает) и маркерные очереди.

Правило заполнения, выдержанное во всех файлах: **резидентно — только ядро
и стоп-правила; процедуры — по вызову; сырьё — в архив.** Нарушение
(процедура, вписанная в AGENTS.md) растёт линейно ценой каждого хода.

## 6. Идентичность и самоизменение (Д0, принято 17.11)

- **Ось = IDENTITY.md** (роль назначена существующему файлу, нового состояния
  не введено). Миссия — «чем агент должен стать»; идентичность — «кем он себя
  считает сегодня». Дрейф = идентичность меняется без участия миссии.
- **Агент развивает сам себя свободно** (MEMORY, AGENTS-дельта, wiki,
  narrative), но самоизменение в защищённых слоях сопровождается receipt с
  цитатой из IDENTITY.md (проекция на ось); правка без цитаты уходит в
  «оспоренное» и копится в drift-метрике — не в запрет.
- **Пересмотр оси** — только через противоречие, proposal в ратификационную
  очередь (9-4), оператор. Не через накопление мелких правок.
- **Единственный жёсткий запрет** — destroy без следа (истребление версий,
  суждений, нарратива без receipt и версии).

## 7. Порождение и drift-контроль

- Порождение — провижионер по `agents-canon.toml`: рендерит `_template` в
  воркспейс нового агента, вписывает `<ALIAS>`, origin_marker
  (`template: _template@v2`), профили (риск/рантайм/скиллы) — ensure-if-missing
  в config.toml, две крон-джобы (self-review вс 18:xx, wiki-compile пн 06:xx,
  минута старта размазана hash(alias) % 60).
- После рендера шаблон живёт своей жизнью: **нет автосинка**. Расхождение
  порождённого агента с шаблоном — норма (это и есть развитие), ловится не
  запретом правок, а git-историей воркспейса (self-review коммитит еженедельно)
  и origin_marker для сверки версий шаблона.

## 7. Как создаётся личность: порождение (рендер шаблона)

Личность агента не пишется руками — она **рендерится из шаблона** одной
операцией (проектное решение «материализация, не наследование», 08.11,
Ram: `_maintenance/agent-template-design.md` — инженерный источник; документ
локальный, в gitignore, поэтому суть продублирована здесь намеренно).

**Что делает provisioner** (`C:/Users/Homework/.zeroclaw/service/provision-agent.py`):
1. Валидация алиаса.
2. Ensure-сидов в config.toml (`risk_profiles.worker_base`,
   `runtime_profiles.worker_base`, `skill_bundles.base` — только если там
   нет; живущая копия — источник истины, сиды не синкаются).
3. Рендер секции `[agents.<alias>]` (+companion), отказ при дублях.
4. Копия `agents/_template/` в воркспейс с подстановкой `<ALIAS>`.
5. Две крон-джобы от имени агента (self-review, wiki-compile; минута старта
   размазана `hash(alias) % 60`).
6. `config migrate` — валидация до рестарта.
7. Идемпотентность: повторный прогон с тем же входом не плодит дубли.

**Ритуал порождения (действующий):**
1. `python service/provision-agent.py <alias> [--domain-file домен.md] [--dry-run]`.
2. Рестарт сервиса — отдельным явным действием (provisioner не рестартует).
3. После рестарта: `cron list` сверка + смоук-ход.
4. Дифф против шаблона: `python service/agent-drift-check.py` (report-only;
   «свой» у предшаблонных агентов, «ДРЕЙФ» — только у носящих origin_marker).

**Политика обновлений:** правка шаблона НЕ переписывает живых агентов
задним числом. Обновление живого агента = явный re-provision с показом diff
и визой владельца (специализация агента — его собственность). Ручная сборка
агентов запрещена (закреплено в father-bridge/BOOTSTRAP.md §Дисциплина,
кейс gpu_counsel 10.11).

## 8. Конвенция выноса в скиллы и ссылок (v2.1, 10.11 — экономия контекста)

Резидентное ядро = AGENTS.md (роль, цикл, триггер-таблица, запреты, домен) +
SOUL.md (характер, стиль — ТОЛЬКО здесь) + IDENTITY.md (карточка, без
процедур) + USER.md (заполненная карточка) + TOOLS.md (инструментальные
границы). Правила:

1. **Триггер-таблица «ситуация → скилл» обязательна**; один триггер = одна
   строка; повтор триггера в TOOLS.md/SOUL.md запрещён.
2. **Процедура >25 строк — только в скилле** (`read_skill`); в ядре —
   строка-триггер. Источник истины регламента — файл скилла, не пересказ.
3. **Стиль и речевые нормы — только в SOUL.md**; AGENTS.md их не пересказывает.
4. **Ссылки из bootstrap — только на существующие файлы** (битые чинить
   сразу; lint-проверка при ревью).
5. **MEMORY.md ≤ 6000 Б** — единая метрика; файл появляется с первым уроком,
   пустые болванки не порождать.
6. **IDENTITY.md не несёт процедур** (карточка + маркер шаблона).
7. **worker-профили — `prompt_injection_mode="compact"`**, и read_skill
   ОБЯЗАН быть в `allowed_tools` — без него compact молча деградирует в Full
   (`AgentBuilder::build` режет реестр по allowed_tools).
8. От defer-синтаксиса в ядре отказались (апстрим не принял, PR #12044) —
   механика «резидентное ядро + адресуемые знания» живёт на штатных
   средствах: compact + read_skill + prose-таблица триггеров.

**Грабли, уже оплаченные (не повторять):**
- **Молчаливая обрезка капа.** Кап 30K резал skills-секцию legalplat без
  WARN (поймано только трейсом system_chars). Следить за размерами ядра;
  при переполнении файла personality тоже обрезка без ошибки
  (см. §4 — пометка truncated).
- **Отгрузка наружу без санитайза.** worker_base v2 ушёл на NotaBene с
  Windows-путями, реальным именем и chat_id — отозван. Правило: любой пакет
  наружу — только после sanitize-грепа (секреты/имена/paths/chat_id),
  USER.md в пакете — плейсхолдер.
- **Юнит-тесты не ловят wire-уровень** (кейс allowed_updates 10.11): наши
  нововведения сначала живой тест на рабочем билде, потом апстрим-PR.

## 9. Чего этот канон НЕ покрывает (границы)

- Не отменяет эпики 9.x: наоборот, 9-3 воплощает матрицу прав из §6 в коде
  (`policy_gate.rs`), 9-4 — очередь ратификации.
- Не описывает каналы/биндинги — они в config.toml, здесь только файловая
  модель личности и памяти.
- Апстриму не предлагается: в апстриме нет контура, владельца и оси; канон
  специфичен для RAM-инстанса (до отдельного решения).
