# ADR (draft): как канал обрабатывает входящее сообщение

- **Статус:** набросок, утверждён Ram 19.11
- **Действие:** переделка внутреннего устройства telegram-канала и PR #12201
- **Где применяем:** ко всем нашим правкам в каналах дальше — этот документ
  является критерием ревью

## В чём проблема

Сообщение в Telegram приходит с полями: текст, голосовое, документ, фото.
Сейчас канал делит их на три отдельные категории, и у каждой свой
обработчик:

- текст — `parse_update_message`,
- голосовое — `try_parse_voice_message`,
- файл/фото — `try_parse_attachment_message`.

Проблема в том, что обработчик голосового сообщения делает сразу три разных
дела: читает поле Telegram, отправляет аудио в транскрайбер и решает,
отвечать ли боту (проверяет упоминание). Три разных дела в одной функции.

Из этого выросла вторая проблема — флаги. Когда мы захотели, чтобы бот в
одной группе не отвечал на необращённые голосовые, пришлось вводить
отдельный флаг `voice_without_mention` — только для голосовых. Если завтра
понадобится такое же правило для документов — появится ещё один флаг.
Каждая новая категория контента требует своего исключения в правилах.

Коротко: разделение «голосовое / файл / текст» — это разделение по полям
Telegram, а не по смыслу. Для агента голосовое — это тот же документ,
только распаковывается через транскрайбер вместо конвертера.

## Что мы предлагаем

Разделить обработку сообщения на четыре последовательных шага. Каждый шаг
делает одно дело и ничего не знает про устройство соседних.

**Шаг 1. Перевод с языка Telegram (только здесь знаем про Telegram).**
Принимаем сырой JSON и превращаем во внутреннее сообщение:

- кто отправил,
- из какого чата,
- адресовано ли боту (есть @упоминание или это ответ на сообщение бота),
- текст, если есть,
- список вложений, если есть (любых: голосовое, файл, фото).

Дальше по коду слов «voice» и «document» как категорий нет — есть
«вложение» с пометкой, какого оно типа. Появилась новая платформа
(Discord, Matrix) — меняется только этот шаг.

**Шаг 2. Распаковка вложений (только здесь знаем про форматы).**
Каждое вложение превращаем в то, с чем умеет работать агент: текст или
путь к файлу. Свой распаковщик на тип: аудио — транскрайбер, docx —
конвертер в md, pdf — извлечение текста, фото — путь (позже OCR).
Результат всегда одинаковый: текст и/или `[Document: имя] /путь`.
Появился новый формат — добавляется один распаковщик, правила бота не
трогаются.

**Шаг 3. Правила участия (только здесь знаем про политику бота).**
По факту «адресовано/не адресовано» и двум существующим настройкам канала
решаем судьбу сообщения:

- `mention_only = false` — отвечать на всё;
- `mention_only = true` — отвечать только на адресованное;
- плюс `passive_group_context = true` — необращённое не выбрасывать, а
  записывать в контекст разговора (бот «слышит» всё, отвечает по обращению).

Это обычная таблица из четырёх ячеек, проверяется простыми тестами. Никаких
флагов под отдельные форматы — голосовое, текст и файл проходят одну и ту
же таблицу.

**Шаг 4. Работа агента.**
Агент получает готовое: текст сообщения и распакованные вложения. Этот
контракт (`ChannelMessage`) уже есть во фреймворке и не меняется.

Итого: сообщение проходит путь «перевод → распаковка → правила → агент»,
и каждый шаг смотрит только на результат предыдущего.

## Что меняется для существующих настроек

- `mention_only` и `passive_group_context` работают как раньше, для всех
  форматов сообщений одинаково.
- Флаг `voice_without_mention` из PR #12201 **отзывается** — он был нужен
  только потому, что голосовое жило отдельной категорией. Когда категория
  исчезает, флаг теряет предмет. Апстримом он не выпущен, поэтому удаление
  — это правка открытого PR, а не ломка релиза.
- Одно намеренное изменение поведения: необращённое голосовое больше не
  получает немедленный ответ. mention_only означает «не отвечать на
  необращённое» — теперь это верно для любого формата. Голосовое при этом
  не теряется: с `passive_group_context = true` оно транскрибируется и
  попадает в контекст.

## Порядок работ

1. Выделить таблицу правил и проверку «адресовано ли» в отдельные функции,
   подключить к существующему коду. Поведение не меняется.
2. Выделить распаковку вложений в отдельный модуль (скачивание,
   транскрипция, рендер путей).
3. Свести голосовое, аудио, документы и фото в одно семейство вложений на
   первом шаге; удалить отдельный обработчик голосового как самостоятельный
   блок с собственными правилами.
4. Убрать `voice_without_mention` из кода и конфига.

Каждый шаг — отдельный коммит, после каждого прогоняется модульный сьют
канала (500+ тестов).

## Почему это хорошо для проекта (текст для апстрим-PR)

- **Проблема:** поле Telegram выросло в поведенческую категорию; каждая
  новая асимметрия между форматами требовала нового флага.
- **Решение:** четыре шага с односторонними связями; контракт с фреймворком
  (`ChannelMessage`) уже так устроен — канал приводится в соответствие с
  ним, новые сущности не вводятся.
- **Выигрыш:** новый формат файла = один распаковщик без изменения правил;
  новая платформа = один шаг перевода; правила бота = таблица с тестами.
  Каналы — экспериментальный слой с плагинной миграцией на v1.0, и первые
  два шага — это ровно та поверхность, которую реализует плагин канала.

## Как мы сами будем пользоваться этим документом

Любая наша следующая правка в каналах проверяется четырьмя вопросами:
к какому шагу она относится; не читает ли код чужие данные (правила не
должны знать про поля Telegram, распаковка — про упоминания); какая
асимметрия породила новый флаг и можно ли закрыть её границей вместо флага;
одинаково ли текст и любое вложение проходят таблицу правил.
