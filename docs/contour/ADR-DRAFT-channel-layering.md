# ADR: как канал обрабатывает входящее сообщение

- **Статус:** доработан после критического прогона, утверждён Ram 19.11
- **Действие:** переделка внутреннего устройства telegram-канала и PR #12201
- **Область:** только входящий путь канала. Исходящий путь (как бот отвечает)
  — предмет документирования агента (SOUL/канон), отдельная тема.
- **Контурный инвариант (первый класс):** голосовое, допущенное к обработке,
  всегда расшифровывается и попадает в контекст как текст. Допущенное —
  это обращённое сообщение или прослушанное (в группе с
  `passive_group_context = true`). В группе, где необращённое дропается,
  транскрипции не происходит — расхода нет. Голос не бывает «просто
  ссылкой на файл»: попал в обработку — стал текстом, с которым работают
  агент и контекст разговора. Решение о допуске (шаг 3) принимается раньше
  материализации (шаг 2).

## В чём проблема

Сообщение в Telegram приходит с полями: текст, голосовое, документ, фото.
Канал делит их на три категории, у каждой свой обработчик. Обработчик
голосового делает три разных дела сразу: читает поле Telegram, шлёт аудио в
транскрайбер, решает, отвечать ли боту (проверяет упоминание).

Из этого вырос второй дефект — флаги. Чтобы бот в одной группе не отвечал на
необращённые голосовые, пришлось ввести флаг только для голосовых —
`voice_without_mention`. Каждая новая категория контента требовала бы своего
исключения в правилах.

Разделение «голосовое / файл / текст» — это разделение по полям Telegram, а
не по смыслу. Для агента голосовое — тот же документ, распаковывается через
транскрайбер вместо конвертера.

## Решение: четыре шага, каждый делает одно дело

Сообщение проходит путь «перевод → распаковка → правила → агент». Каждый
шаг видит только результат предыдущего и ничего не знает об устройстве
соседних.

**Шаг 1. Перевод с языка платформы.**
Единственное место, знающее про Telegram. Сырой JSON → внутреннее сообщение:
кто отправил, из какого чата, адресовано ли боту, текст, список вложений
(любых). Сюда же относится батчинг альбомов: несколько сообщений,
объединённых платформенным `media_group_id`, — это семантика платформы, она
решается на переводе. Типы сообщений платформа типизирует сама; переводит
шаг известные, прочее игнорируется. Новая платформа (Discord, Matrix) —
меняется только этот шаг.

**Шаг 2. Распаковка вложений.**
Каждое вложение → то, с чем работает агент: текст и/или путь к файлу.
Голосовое — транскрайбер (всегда, по инварианту контура). Документы — путь
к файлу: чтение и конвертация (docx → md и т.п.) — штатные инструменты
агента, канал их не дублирует. Фото — путь. Семейство вложений и разбиение
по типам в коде уже есть (`TelegramAttachmentKind`: Image / Video / Audio /
Voice / Document) — речь о том, чтобы это осталось деталью распаковки, а не
основой для отдельных правил. Новый формат — один распаковщик, правила
бота не трогаются.

**Шаг 3. Правила участия.**
По факту «адресовано/не адресовано» и настройкам канала:

- `mention_only = false` — отвечать на всё;
- `mention_only = true` — отвечать только на адресованное;
- `passive_group_context = true` — необращённое не выбрасывать, а писать
  в контекст разговора: бот слышит всё, отвечает по обращению.

Обычная таблица из нескольких ячеек, проверяется простыми тестами. Текст и
любое вложение проходят одну и ту же таблицу — исключений по форматам нет.
«Адресовано» — это упоминание бота в тексте или подписи, либо ответ на
сообщение бота. Ответ на сообщение бота — рабочая эвристика обращения, а не
аксиома: в активных группах люди реплаят на последнее сообщение, чтобы
сказать друг другу. Эвристика остаётся, но калибруемая, и в документе она
названа честно.

**Шаг 4. Работа агента.**
Агент получает готовое: текст и распакованные вложения. Контракт
(`ChannelMessage`) уже есть во фреймворке и не меняется. Канал строг в
автоматических ответах, но инициатива у агента сохраняется: если агент
считает, что контексту нужен ответ, он может написать первым — это
дисциплина его SOUL, а не правило канала.

## Что меняется для существующих настроек

- `mention_only` и `passive_group_context` работают как раньше, для всех
  форматов одинаково.
- Флаг `voice_without_mention` из PR #12201 отзывается. Он был нужен только
  потому, что голосовое жило отдельной категорией; категория исчезает —
  флаг теряет предмет. Апстримом он не выпущен, удаление — правка открытого
  PR.
- Одно намеренное изменение поведения: необращённое голосовое не получает
  немедленного ответа. mention_only означает «не отвечать на необращённое» —
  теперь это верно для любого формата. Голосовое при этом не теряется:
  по инварианту контура оно расшифровано и лежит в контексте; с
  `passive_group_context = true` бот его слышит и ответит, когда обратятся.

## Порядок работ

1. Выделить таблицу правил и проверку «адресовано ли» в отдельные функции,
   подключить к существующему коду. Поведение не меняется.
2. Выделить распаковку вложений в отдельный модуль (скачивание,
   транскрипция, рендер путей). Перенести сюда же cap-фикс удержания
   offset prepopulate'ом (сейчас он на форк-ветке #12404, `761cdaeaa`).
3. Свести голосовое, аудио, документы и фото в одно семейство вложений на
   первом шаге; убрать обработчик голосового как самостоятельный блок с
   собственными правилами.
4. Убрать `voice_without_mention` из кода и конфига.

Каждый шаг — отдельный коммит, после каждого прогоняется модульный сьют
канала (500+ тестов). До четвёртого шага в проде остаётся текущий флаг —
противоречия нет, конфиг правится в конце.

## Почему это хорошо для проекта (текст для апстрим-PR)

- **Проблема:** поле Telegram выросло в поведенческую категорию; каждая
  новая асимметрия между форматами требовала нового флага.
- **Решение:** четыре шага с односторонними связями; контракт с фреймворком
  (`ChannelMessage`) уже так устроен — канал приводится в соответствие с
  ним, новые сущности не вводятся.
- **Выигрыш:** новый формат файла — один распаковщик без изменения правил;
  новая платформа — один шаг перевода; правила бота — таблица с тестами.
  Первые два шага — это ровно та поверхность, которую реализует будущий
  плагин канала (channels — экспериментальный слой, плагинная миграция на
  v1.0).
