## 1. Диагноз одним абзацем

ZeroClaw умеет хранить эпизоды и поднимать похожее. Его три памятные подсистемы — эпизодический поток (brain.db + консолидация), граф знаний (knowledge_graph.rs), инжект в контекст (memory_inject.rs) — **не сцеплены**: консолидация не пишет в граф (0 узлов при включённом auto_capture), инжект не читает граф, уничтожение в hygiene физически удаляет то, что концепция требует сохранять обратимо. Между «запомнил факт» и «понял, что это значит» в коде нет перехода — его вчера закрыл контур файлами (wiki-канон + очередь). Полноценной памяти = связки уровней с разной ценой изменения — нет. Этот документ — какой она должна быть и на основе чего собирается.

## 2. Уровни целевой памяти → механизмы (отображение)

| Уровень | Смысл | Цена изменения | Носитель целевой | Что уже есть в коде |
|---|---|---|---|---|
| L0 Контекст | текущий ход, окно сессии | — | session/turn (существует) | существует |
| L1 Рабочий стол | активные задачи, черновики | низкая | workspace-файлы | существует (контур) |
| L2 Архив эпизодов | всё пережитое, подъём похожего | ноль | brain.db + консолидация | **есть и работает** |
| L2 Граф знаний | сущности, связи, статистика методов; консолидация структуры | низкая | knowledge_graph.rs (расширенный) | модуль есть, **потока нет** |
| L2.5 Очередь суждений | предложения-кандидаты в нарратив (процесс с протоколом жизненного цикла, НЕ уровень хранения) | у proposal — ноль (агент пишет/отзывает), у принятого суждения — высокая | **новое**: очередь proposals (статусы + исходы) | зачатки: `trend` извлекается и теряется; коррекции оператора — незахваченный сигнал |
| L3 Нарратив | то, что агент защищает о себе/компании; версии | высокая (внимание человека) | wiki-канон (контур) + **always-load в инжект** (патч) | нет в рантайме |
| ⟂ Ядро-регулятор | принципы, полномочия, дистиллят | высокая, правит оператор | SOUL.md (канон-файл, всегда в контексте) | существует (контур) |

Критерий разреза везде — **цена изменения, не тип данных** (пункт 7 концепции). Один факт дорожает и мигрирует вверх по мере того, как в него вложено внимание (человеческое или накопленное).

## 3. Пять узловых достроек (после оппонирования: порядок Д3→Д4→Д5→Д2→Д1)

**Порядок принят из оппонирования (возражение 6): ограничения раньше полномочий, не-удаление раньше того, что на нём стоит, граф последним и на чистом сырье.**

**Д3. Always-load ДИСТИЛЛЬТА нарратива с жёстким потолком (исправлено по в.3).**
Не «pinned по метке» (неограниченное множество = тихий рост инжекта), а один документ-дистиллят с cap (по аналогии с бюджетом MEMORY.md Hermes ~2200 симв.): гарантированно грузится только он; всё остальное нарративное ездит через recall. Разделение якорь/буфер сохраняется: SOUL.md-эквивалент (регулятор, компактный, всегда) отдельно от дистиллята нарратива (версии, cap, курация). Патч `memory_inject.rs`: отдельный бюджет для narrative-дистиллята, загрузка до relevance-пайплайна. Первый и маленький — стартует первым.

**Д4. Обратимость вместо уничтожения (второй — защита фундамента).**
Сегодня hygiene физически DELETE-ит строки по retention, включая Core. Целевое: retention действует как архивирование/затухание (флаг + скрытие из recall), физическая очистка — только для Conversation и по отдельному длинному срику. Механизм обратимого скрытия уже существует — `supersede` из conflict-resolution (default-on). Переносим в гигиену. Отвергнутые ратификатором proposals обязаны пережить retention — очередь (Д2) не должна стоять на самоудаляющемся хранилище.

**Д5. Полномочия на запись (третий — до выдачи новых прав).**
Сегодня агент имеет `memory_forget/purge` и прямую запись в Core. Целевое: разделение операций — эпизодический слой агенту доступен полностью; граф — propose/capture; суждения и нарратив — propose-only; forget/purge на суждениях/нарративе недоступны агенту (второй ключ — оператор). Точка входа: `policy_gate.rs` расширяется с объёмных лимитов до операционных полномочий (категория × операция × origin). Ставится ДО Д2/Д1, чтобы новые права записи не висели в воздухе без ограничений.

**ДT. Слой триггеров (поправка из диалога, v0.4).**
Принцип (находка Hermes, В3+В6): **механизм без триггера пересмотра — мёртв.** Каждому механизму с состоянием — явный триггер: cap дистиллята → триггер принудительной консолидации при эрозии; trust/confidence-поля → триггер периодической ревизии (у него в wiki это дыра); proposals → триггер throttle при превышении бюджета; retention-архивы → тригпер аудита находимости. Механизм без триггера в этом концепте считается незавершённым по определению. Точка входа: hygiene.rs (фазовый прогон — естественный носитель триггеров).

**Д2. Очередь суждений — мульти-генераторная, с жизненным циклом и throttle (четвёртая).**
Не «уровень», а конвейер с протоколом (в.1): propose → review → accept/reject/withdraw → исход записывается обратно в архив как эпизод суждения. **Отказ оператора сохраняется** — это самый ценный сигнал (дороже принятия); отвергнутое затухает-с-аудитом, не испаряется. **Каноническая процедура рождения суждения** (по формуле Hermes, В2): суждение = коллапс приора при противоречащем наблюдении → проверка механизмом → запись последним шагом; переход факт→суждение идёт через противоречие, не через накопление. **Throttle генератора** (предсказание поломки №1, В6): бюджет proposals/неделя + приоритизация каналов — коррекция оператора всегда проходит, trend первым вырезается при переполнении; гейт бремени (acceptance <20%) остаётся как измеритель. Генераторы предложений (по убыванию ценности):
1. **коррекции оператора** («нет, не так» весит больше десяти трендов) — сильнейший социальный сигнал; детекторы: явные (фразы коррекции) + молчаливые (**канал «diff без агента»**: правка файлов агентом после указания, смена темы, повтор вопроса — предсказание поломки №2, В6);
2. **противоречия с каноном/графом** (структурный сигнал; trend их не ловит — он агрегирует, не сталкивает);
3. **дорогие эпизоды** (отказы, провалы с ценой — flashbulb; единичные, trend их не видит по построению);
4. **trend** — как дно-сетка, резервный источник, первый на вырезание при переполнении бюджета.
Точки входа: коррекции — разбор turn-а (контурное правило + сигнал из диалога + канал diff); противоречия — `conflict.rs` уже существует; trend — consolidation.rs:30 (сигнал извлекается и теряется — доводим до записи в proposals).

**Д1. Граф — последним, на ратифицированном сырье, с гейтом качества (пятая).**
Исправлено по в.4: извлечение не из сырого Core-потока (шум: entity-extraction ловит regex-мусор; в grafeo даже с каскадом 65–70% рёбер — мусор), а из **ратифицированных суждений и курированных страниц**, когда их накопится достаточно. На масштабе «память про оператора» полноценный граф вырождается (субъект один, триплеты → списки атрибутов; урок MedGraph — без атрибуции субъекта граф схлопывается); на год первый **W4 (entity-индекс поверх FTS — «граф без графа») дешевле и точнее**. Д1 = расширение knowledge_graph.rs (provenance, веса, би-темпоральность) как подготовка к мультиагентности, не как первоочередная нужда.

## 5. Память Hermes — что забираем (материалы прочитаны: его плагины на cachyos-srv; интервью дополнит)

**Архитектура (по докам плагинов, `/home/ram/.hermes/plugins/`):**

1. **holographic** — ядро памяти. SQLite fact store: FTS5 + HRR-вектора (1024d, вес 0.3 в скоре), trust-скоринг фактов (default 0.5, порог recall 0.3) с обратной связью (`fact_feedback` двигает trust — рынок в Фазе 2 такого не показывал), entity resolution (имена 2–5 слов, алиасы, probe/reason/related), recall-гейт перед ходом (факт покрывает долю информативных слов сообщения; до 5 фактов + entity-факты; повторное всплытие окном в 6 ходов).
2. **Би-темпоральная история (0.8.0)** — ровно наш п.5, реализованный: действия `change/end/correct/revert`; обычный recall видит только present, прошлые версии — в отдельной таблице, читаются по `as_of=YYYY-MM-DD`; каждая версия хранит источник (via/platform/chat/session/автор). Forget — полное удаление с tombstone-хэшем (защита от реанимации факта).
3. **contradict** — детекция противоречий «предлагает, никогда не редактирует» — агент решает; соответствует нашему propose-only.
4. **hermes-dreaming** — ночная петля с вопросами человеку (end/correct/forget). **⚠ ПОПРАВКА (Hermes, 17.11, v0.4): петля — ДИЗАЙН, НЕ ЭКСПЛУАТАЦИЯ** — у него самого плагин не установлен, за 6 месяцев не сработала ни разу (53 факта, feedback у 1, forgotten=0). Реальная петля у него — 4 канала: живые поправки в потоке (~80% сигнала; бюджет вопросов натренирован коррекциями владельца, не спроектирован), пакетная ратификация (один пакет = одно внимание = десятки решений), реестр «на суд» с перепредъявлением (дыра→предложение→цена→варианты), θ-дисциплина. Провалы: гигиена только событийная (устаревший факт молча врёт до столкновения); дроссель пришёл от человека, не из дизайна; пакеты без календарного триггера умирали неделями. Инженерные выводы для zeroclaw: ночная петля — бэкстоп, не двигатель; батчинг бьёт дисциплину (единица внимания — пакет); молчание неинформативно — proposals старше N дней затухают-с-аудитом, коррекция оператора бессрочна; триггер пакета двойной (календарь ИЛИ событие-коррекция).
5. **memory-rewind** — версионирование MEMORY.md/USER.md/**SOUL.md**/skills (git), browse/diff/restore — прямой аналог нашего требования «откат версии нарратива восстанавливает поведение» (hysteresis-гейт) и жизненного цикла enacted-identity якоря.
6. **obsidian-memory** — вьюер хранилища (не ядро памяти).

**Выводы «что забираем» в zeroclaw (все — идеями, поверх своего SQLite):**

- **W1. Trust с обратной связью** — недостающая ось значимости: у нас decay только по времени; у Hermes значимость ещё и социальная (feedback двигает trust). Добавить в importance/decay: ось подтверждений.
- **W2. Би-темпоральность как набор операций** — не «добавить колонку», а контракт операций change/end/correct/revert + present-only recall + as_of-чтение. Наш `supersede` — зачаток; расширяем до полного набора (это же Д4).
- **W3. Dreaming-петля — дизайн с нуля (поправка v0.4):** ночной прогон — БЭКСТОП, не двигатель; ратификация ПАКЕТНАЯ (единица внимания оператора = пакет с десятками решений), двойной триггер (календарь ИЛИ событие-коррекция); молчание неинформативно: proposal старше N дней затухает-с-аудитом, коррекция оператора бессрочна; движок петли — живые поправки в потоке (~80% сигнала). Сращиваем с self-review-кроном контура.
- **W4. Entity resolution поверх FTS** — entity-индекс с алиасами и probe/reason — «граф» без графа: типизированные узлы zeroclaw-KG получают второй, быстрый доступный путь. Идея: сущности KG индексировать именами/алиасами, recall по entity, а не только по тексту.
- **W5. Recall-гейт по покрытию** — экономия контекста: «ok, thanks» не поднимает ничего (у zeroclaw recall всегда тратит вызов). Дешёвый пред-фильтр до дорогого recall.
- **W6. memory-rewind для ядра** — версионировать SOUL.md/канон-файлы через git с diff/restore — у нас wiki уже в git; SOUL.md — нет. Кандидат контурного ритуала (без кода zeroclaw).

**Количественная сверка его хранилища (`memory_store.db`, read-only, 17.11):**

- **53 факта** за период **2026-05-11 → 2026-11-16** (6+ месяцев; самый свежий — фиксация нашей сегодняшней концепции 7 пунктов). Долгая память подтверждена данными, но она **маленькая и курированная**: general 34 / user_pref 13 / project 4 / tool 2.

**Ключевой вывод (поправка к интуиции «у него память объёмнее»):** его долгосрочность — не объём, а **стратификация**: 53 курированных факта с provenance + огромное резюме сессии (362K/1M контекста) + файлы MEMORY.md/wiki + dreaming-петля. Наши 2450 памятей в brain.db — это поток без курации; гипотеза концепта усиливается: нужна не «больше памяти», а **слой значимости и очередь суждений** (Д2, W1).

**Интервью (17.11, files/t1g/hc-to-ram-interview-memory-2026-11-17.md) — его собственные тезисы:**

Его ранжировка механизмов долгосрочности (по вкладу): **(1) always-on заметки с ЖЁСТКИМ бюджетом** (MEMORY.md/USER.md ~2200 симв. каждая — бюджет не ограничение, а механизм отбора; при заполнении — замещение/консолидация, сейчас 99% полон); **(2) recall на КАЖДОЕ сообщение** (не раз в сессию — «долгосрочность из дешёвого релевантного подъёма, не из большого контекста»); (3) скиллы как методы (индекс всегда, тело по требованию); (4) компактификация с якорным индексом + session_search по архиву транскриптов (46 МБ с мая) как страховка; (5) SOUL.md-идентичность всегда в контексте; (6) внешняя wiki (132 стр.) как медленная память знаний. Плюс фоновый review-проход (перепроигрывание хода → записи памяти) с контрактом урока и чёрным списком захвата.

Его типичные потери: компактификация теряет дословность (лечение — якорный индекс); переполнение MEMORY.md; recall-промах при несовпадении keywords (лечение — протокол keywords двуязычно); устаревшие факты (дисциплина change/end/correct).

Его список переносимости в zeroclaw (по ROI, его формулировки): always-on бюджетные заметки → recall-на-сообщение → fact_store-паттерн (короткие автономные факты, trust, версии, keywords двуязычно, faded_get) → скиллы-методы → архив сессий + FTS → фоновый review → git-канон идентичности. **Не переносить напрямую: HRR-векторы (начать с FTS+trust), его wiki как контент.** Честная оговорка его: механику recall holographic-миддлвари описал по схеме БД и наблюдению, не по исходнику middleware.

Материалы (пути на cachyos-srv): wiki `~/texts/LLM Wiki/` (entities: SAGE, EMG, H-MEM, MedGraph, GraphRAG, LightRAG, WikiFM, AdaMM; summaries: temporal-graph-ai-memory, from-loops-to-graphs; concepts: темпоральные цепочки, Coverage–context trade-off); транскрипты `~/texts/Hermes/Transcript analisys/`; исследования grafeo-notebook `docs/research/gbrain-analysis-2026-11-16.md`, `gbrain-conceptual-model-2026-11-16.md`.

## 7. Гейты приёмки (исправлены по в.5, в.7)

1. **Воспроизведение кейса LegalPlat:** дельта-суждение проходит цикл propose→mirror→ратификация; недели спустя «кто мы» отвечается из нарратива. **+ Негативный контроль (SIT):** проба включает вопросы, на которые правильный ответ — «не знаю / не решено»; нарратив имеет обязательный раздел «открыто/оспорено/не знаю».
2. **Находимость отвергнутого ≥95%** по прямому запросу (рынок ~7% на ForgetEval).
3. **Откат версии нарратива восстанавливает поведение** (hysteresis-гейт).
4. **Self-id probe:** после рестарта корректные ответы «кто я / кто оператор» до внешнего запроса, включая негативные пробы.
5. **Граф (когда Д1 дойдёт) — КАЧЕСТВО, не объём:** доля узлов с provenance, хоть раз повлиявших на proposal или ответ (utility rate); ноль узлов с влиянием лучше сотен без. Гейт «сотни узлов» отменён как регресс к метрике потока.
6. **Бремя оператора:** proposals/неделю и доля принятых; acceptance <20% две недели подряд = генератор шума, ловится гейтом, а не усталостью оператора.

## 8. Границы (чего не делаем)

Не тащим GrafeoDB и сервисы — всё внутри форка и его SQLite. Не ломаем апстрим-поверхность памяти (расширения — за флагами конфига). Не даём агенту self-ратификацию и destroy на суждениях/нарративе никаким путём. Канон-специфика — в форке, не в PR апстриму (до отдельного решения).

## 10. Целевое видение v0.4 (соавторство RAM×HC, 17.11 — половина HC: `hc-to-ram-vision-half-2026-11-17.md`)

**Портрет целевой памяти:** тысячи эпизодов, сотни суждений, десятки канонических фактов, граф в десятки узлов — и любое утверждение агента докопываемо за три клика: нарратив → суждение → цитата.

**Готовые алгоритмы из проектов владельца (HC, без тяжёлых зависимостей, перенос в SQLite-ми zeroclaw):**
- *Запись:* идемпотентность арифметикой (hash-slug+upsert, gbrain); quote grounding на экстракции (folded-подстрока; 0/2+ совпадений → null — fail-closed, истина проверяется в момент записи); fail-closed резолвер сущностей (FTS5+алиасы); **subject в ключе факта** (MedGraph — страховка от подмены голоса); SUPERSEDES с весом 0.0 (ADR-0035 ↔ наш набор change/end/correct/revert).
- *Чтение:* recall-гейт по покрытию сообщения; пакет Matched+Anchor+Relation (SQL по validity+supersession); hub dampening (log degree против центральностного перекоса); relation families.
- *Цикл:* каскад тиров как принцип с телеметрией (год первый — Tier-0/1 без моделей: детерминированные слои сначала, LLM только на неуверенном); инкрементальность content-hash (ночной прогон дешёвый — снимает главный аргумент против ночного бэкстопа); **contested-кластеры (SQL-join по entity — генератор противоречий без единого LLM-вызова)**; линт-гейт консолидации (проверка встроена в запись = гейт по построению).

**Граф — согласие в политике, спор в схеме, разрешённо так (HC убедил):**
- **Схема графовая (nodes+edges) с первого дня** — стоит ноль, а миграция схемы памяти под живым агентом — худший из ремонтов. Это правка к моей позиции «год первый только entity-индекс»: индекс живёт как политика доступа, схема — как фундамент.
- **Политика строгая:** рёбра — только из деклараций оператора и ратифицированных суждений; 30–150 узлов = здоровье, рост за пределы — сигнал разобрать.
- **Первая работа графа — НЕ retrieval:** зеркало per-decision (для ратификации) + supersession-навигация (что чем заменено) + отчёты self-review.
- **Триггер полноценного KG:** цена неоднозначности FTS (recall-промахи дорожают) или второй субъект памяти — не мультиагентность сама по себе.
- **Первый графовый документ — карточка оператора по 6 топикам HIM-light.**

**Год по кварталам (HC, принято):**
- **М1–2:** дистиллят с cap + не-удаление + полномочия (Д3→Д4→Д5). Принцип квартала: 0 необратимых операций.
- **М3–4:** очередь 4 генераторов + пакетная ратификация (Д2). Вилка acceptance 30–70%: <20% — генератор шума, >90% — ратификация-штамп. Первый отказ с аудитом.
- **М5–8:** микро-KG из ратифицированного (Д1); utility rate ≥0.5; hysteresis-гейт пройден (откат версии восстанавливает поведение).
- **М9–12:** ночной бэкстоп с линтом; триггер ревизии trust в бою; отвергнутое находится ≥95%.

**Расхождение, оставленное открытым:** триггер полноценного retrieval по графу — ценовой (неоднозначность FTS) vs событийный (второй субъект). Решается данными М5–8, не дискуссией.
