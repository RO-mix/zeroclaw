## Блок Б. Новый компонент — `agent-memory-service`

**Форма:** отдельный процесс на cachyos-srv (рядом с grafeo), интерфейс — MCP (stdio), подключение агентам ZeroClaw через `mcp_bundles` в конфиге — тот же проверенный паттерн, что у `db_broker`/`converter`/`transcriber`.

**Почему не внутрь zeroclaw:** (1) граф физически на cachyos-srv, агенты — на windows/VPS; (2) протокол ратификации — канон-специфика нашего контура, в апстрим zeroclaw не идёт (решение 16.11: контурное ≠ апстримное); (3) `knowledge_graph.rs` в zeroclaw-memory — библиотечный зачаток, не носитель протокола.

**Содержимое v0:** SQLite-таблица `proposals` (статусы `proposed → mirrored → signed → deployed | rejected`; payload дельты; hash предыдущего receipt → цепочка), сборщик mirror-пакетов, append-only журнал receipts.

**Почему не файлы навсегда:** файловый прототип (image-pending.md) — Этап 1; receipt-цепочку на файлах дёшево не проверить, а Panella-паттерн требует неизменяемой цепочки → Этап 2 переводит очередь в сервис.

## Блок В. MCP-поверхность (5 инструментов, без approval)

`graph_query` (чтение с decay-весами), `image_delta_propose` (в очередь), `decision_mirror` (сборка пакета на подпись), `faded_get` (прямой доступ к отвергнутому по ID, обход decay), `selfreview_run` (недельная сверка + drift-метрики). **Approval-инструментов в поверхности нет по дизайну** — второй ключ не доступен агенту ни по какому пути (разрез ключей Panella).

## Блок Г. Подпись оператора — второй ключ

- Mirror-пакет доставляется существующим каналом: telegram-файл через `telegram_sender` (тот же механизм, что self-review шлёт отчёты сегодня).
- Ответ «утверждаю» = подпись. Сервис: `signed` → RECEIPT (changelog-раздел канонической страницы + git-коммит wiki + `superseded_by` в brain.db) → DEPLOY (identity-doctor: обновление дистиллята в SOUL.md + затухание отвергнутого в графе).
- **Честная граница:** криптографической подписи нет — доверие к каналу оператора (его chat_id), как сейчас с крон-промптами. Panella-паттерн реализован на уровне разделения операций, не ключей. Усиление (подпись/кодовое слово) — отдельной постановкой, если понадобится.

## Механика по пунктам концепции

1. **Нарратив-вершина** — wiki-страница + git-история; попадание в контекст агента — штатная загрузка канон-файлов zeroclaw (проверено в коде: всегда в системном промпте).
2. **Архив** — brain.db + wiki: существует.
3. **Очередь предложений** — Этап 1: `image-pending.md`; Этап 2: таблица `proposals` сервиса. Триггер дельты — правило в AGENTS.md (внедрено).
4. **Граф-инфраструктура** — расширение ADR-0030: вес рёбер в PPR получает decay-фактор `w = w_base × f(возраст, ратификационный статус)`. Кандидаты в L3-очередь — выборка по центральности + типам связей (каскад ADR-0037 уже фильтрует мусор).
5. **Затухание** — комбинация трёх переносимых механик: (а) би-темпоральность по Graphiti: к ADR-0035 добавить `recorded_at` (transaction time); (б) decay-как-rerank по Mem0 Decay (0.3–1.5x) поверх PPR; (в) `faded_get` по Mem0 fetch-by-ID — прямой доступ минует decay. Обратимость: снятие expiry = новая запись, не стирание (паттерн `superseded_by` — существующий).
6. **Ядро-регулятор** — SOUL.md; якорь enacted identity обслуживается штатной загрузкой канона (Latent Identity Reversion закрыт); self-id probe — шаг в `selfreview_run`.
7. **Разрез хранение/governance** — реализован физически: хранение = граф/wiki/sqlite; governance = сервис (proposals/receipts) + действия оператора вне MCP-поверхности.

## Этапы

- **Этап 1 — файловый прототип (~неделя):** доработать mirror-пакет из image-pending у legalplat (diff дельты + provenance + faded-список, доставка telegram-файлом). Готовность ~70% (очередь + шаг ОБРАЗ-КАНОН есть). Критерий: первая дельта прошла полный цикл PROPOSE→MIRROR→SIGN→RECEIPT.
- **Этап 2 — сервис v0:** `agent-memory-service` (стек — по аналогии с db_broker; уточнить у владельца t16), MCP-подключение через `mcp_bundles`, таблица `proposals`. Критерий: legalplat работает с очередью через MCP, не через файлы.
- **Этап 3 — механики графа:** decay в PPR, transaction time, dream-цикл как L2-консолидатор (L3-очередь не трогает). Критерий: гейты self-review зелёные (drift, находимость ≥95%, hysteresis-замер).
- **Этап 4 — масштаб:** скелет в base-kit для всех агентов контура; зеркалирование NB по регламенту.

## Чего мы НЕ строим (явно)

Свою БД (GrafeoDB+SQLite хватает), свой чанкер (портируем gbrain), свою векторную индексацию (Grafeo HNSW), свой LLM-инференс (каскад ADR-0037 существует). И не строим никогда: approval в MCP-поверхности, автопринятие накоплением, агент-агентскую ратификацию.
