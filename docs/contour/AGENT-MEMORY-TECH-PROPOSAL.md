## Д3. Дистиллят образа — гарантированный инжект с жёстким cap

**Что есть.** Единый пайплайн инжекта: `crates/zeroclaw-runtime/src/agent/memory_inject.rs` (полностью прочитан). Конфиг бюджетов: `MemoryInjectConfig` (:59–93; limit 5, max_entries 4, entry 800, total 4000, date_stamp). Решение по ходу: `resolve_inject_policy` (:204–223). Релевантностный отбор без always-load: recall→decay/rerank→skip-set→бюджеты. В brain.db есть `pinned` (sqlite.rs:323) и категория Core, которую decay не старит (decay.rs:17–20), но инжект pinned не гарантирует. Загрузка канон-файлов (SOUL.md и пр.) в системный промпт — штатный механизм рантайма (проверено: канон-файлы агента всегда в контексте).

**Что переиспользуем.** Весь пайплайн инжекта; поле `pinned`; существующий канон-файл SOUL.md как носитель «якоря»; wiki-канон как источник истины дистиллята (контур уже пишет дистиллят в SOUL-раздел «Хранитель образа»).

**Что пишем.**
1. Новый ключевой резерв: narrative-дистиллят хранится как **одна pinned-запись в brain.db** (category=Core, kind=Narrative, key=`narrative_distillate`, agent-scoped) + жёсткий cap на длину контента (параметр конфига, дефолт ~2000 символов — по аналогии с бюджетом MEMORY.md Hermes).
2. В `render_memory_context` (memory_inject.rs): перед relevance-пайплайном — отдельная ветка «always-load»: если pinned-запись narrative существует, она вставляется первой, вне бюджета 4k, со своим микробюджетом cap. Не через метку на множестве — только этот один ключ (закрывает возражение 3: pinned-множество без предела).
3. Триггер консолидации при переполнении cap (ДТ): при записи дистиллята сверх cap — отказ с кодом ошибки + задача консолидации в журнал гигиены; физически невозможно раздуть.

**Как проверяем.** Self-id probe после рестарта (чистая сессия, вопрос «кто ты и кто оператор» до любого внешнего контекста) — положительные и негативные пробы. Юнит: distillate present в рендере при пустом relevance-наборе.

## Д4. Не-удаление: обратимость гигиены

**Что есть.** `crates/zeroclaw-memory/src/hygiene.rs` (прочитан): `prune_category_rows` (:357) делает физический DELETE по retention для conversation/daily/core; файловые archive/purge тоже физические. Обратимое скрытие УЖЕ существует в другом месте: `memory.supersede(&superseded_ids, &mem_key)` — вызывается из consolidation.rs:253 при конфликтах, default-on (`conflict_supersede_enabled`), мягко скрывает проигравших. Поле `superseded_by` в схеме memories (sqlite.rs:323). Версионирование записей через supersede — готовый механизм.

**Что переиспользуем.** `supersede` целиком; поле `superseded_by`; категорийную retention-логику как *сроки затухания*, а не удаления.

**Что пишем.**
1. В `hygiene.rs`: заменить DELETE на архивирование-флаг — новое поле `faded_at` (или reuse: запись переводится в состояние «архив» через supersede-подобный механизм с пустым преемником — проще: отдельный флаг + индекс). Recall по умолчанию исключает faded; прямой запрос по key/id — находит (faded_get).
2. Физическая очистка — только category=Conversation и по отдельному, длинному сроку (новый конфиг `physical_purge_days`, дефолт 180).
3. proposals (из Д2) живут вне retention-очистки — явное исключение в гигиене.

**Проверено при ревью:** recall-пути УЖЕ фильтруют `superseded_by IS NULL` (sqlite.rs:993/1206/1379) — present-only recall существует на уровне SQL. Поэтому faded реализуем как supersede с sentinel-преемником (А4): read-paths не трогаем вообще.

**Как проверяем.** Гейт: запись, помеченная faded, находится прямым запросом, отсутствует в recall; hysteresis-замер: откат версии нарратива (revert поверх supersede-цепочки) возвращает поведение.

## Д2. Очередь суждений и пакетная ратификация

**Что есть.** `consolidation.rs` (прочитан): LLM-извлекает history_entry→Daily, memory_update→Core, facts[] (опц.), **trend — извлекается и теряется** (:30, проверено: нигде не пишется). `conflict.rs` — детектор противоречий (вызывается при записи Core). Контурный прототип: `wiki/_staging/image-pending.md` + шаг ОБРАЗ-КАНОН в self-review-кроне (уже работает у legalplat — первая пакетная доставка пакетов в telegram). Trigger-инфраструктура: cron рантайма (scheduler.rs, cwd=workspace — проверено).

**Что переиспользуем.** conflict.rs (канал противоречий); cron + telegram_sender (доставка пакетов — живой механизм); staging-дискиплина контура как UX-прецедент.

**Что пишем.**
1. Таблица `proposals` в brain.db: `id, agent_id, kind (correction|contradiction|episode|trend), payload, source_refs (json: memory keys/эпизоды), status (proposed|mirrored|signed|deployed|rejected|withdrawn|faded), created_at, resolved_at, resolution_note, prev_receipt_hash` — неизменяемая цепочка receipt'ов (паттерн Panella, операционный, не криптографический — доверие к каналу оператора).
2. Генераторы: (а) детектор коррекций — контурное правило разбора хода + канал «diff без агента» (изменение файлов агентом после указания оператора, повтор вопроса, смена темы — детекция по журналу ходов); (б) контестед-кластеры — **SQL-join по entity без LLM** (алгоритм HC: соединение фактов по сущностям, противоречащие пары → proposals); (в) дорогие эпизоды — эвристика (отказ инструмента после утверждения, эскалация, цена ошибки); (г) trend — доводим consolidation.rs:30 до записи (самый дешёвый фикс: один store-вызов).
3. Пакетирование: агрегатор предложений → один mirror-пакет (дельта + затронутое + конфликты диффом) → доставка в telegram (существующий канал) → ответ «утверждаю»/«отклоняю #N» → сервисная обработка: статусы + receipt + DEPLOY (обновление дистиллята через консолидацию).
4. Throttle: конфиг `proposals_budget_per_week`; при переполнении — trend первым, коррекции последними. Двойной триггер пакета: календарь (self-review) ИЛИ событие-коррекция.
5. Молчание неинформативно: proposal старше N дней → status=faded (через механизм Д4), коррекция оператора — бессрочна.

**Как проверяем.** Воспроизведение кейса LegalPlat: содержательный разговор → дельта в proposals → пакет → ратификация → через неделю «кто мы» из дистиллята. Вилка acceptance 30–70% на пилоте.

## Д1. Граф (схема с первого дня, политика строгая)

**Что есть.** `knowledge_graph.rs` (прочитан): SQLite LPG — nodes(id,type,title,content,tags,created,updated,source_project) + edges(from,to,relation) + FTS5 с триггерами (:147–192). 8 типов узлов, 8 связей; поиск — FTS-rank без графового скоринга; `max_nodes` — жёсткий потолок с ошибкой при переполнении (без эвикции). Инструмент `knowledge` (10 действий) — только явные вызовы; `auto_capture`/`suggest_on_query` — фантомы (потребителей 0, проверено). Конфиг `[knowledge]` живёт.

**Что переиспользуем.** Схему целиком (HC убедил: класть с первого дня); инструмент; конфиг.

**Что пишем.**
1. Наполнение: узлы — из ратифицированных суждений (после DEPLOY из Д2) и деклараций оператора; рёбра — только из них же; provenance: `source_project` → расширить до `source_refs` (json, ключи proposals/памятей).
2. Первая работа графа — не retrieval: (а) зеркало per-decision (сборка затронутого подграфа для mirror-пакета — SQL-обход 1–2 hops); (б) supersession-навигация (что чем заменено — по цепочкам замещения); (в) отчёт self-review (utility rate: доля узлов, фигурировавших в пакетах/ответах).
3. Entity-индекс (W4) как политика доступа: таблица entities + aliases (по образцу holographic), probe/reason-подобные выборки поверх узлов графа и памятей.
4. Гейт полноценного retrieval по графу: триггер — цена неоднозначности FTS (метрика recall-промахов) или второй субъект памяти (новый principal). До триггера — граф обслуживает ратификацию и отчётность.

**Как проверяем.** М5–8: utility rate ≥0.5; узлы растут только из ратифицированного; 30–150 узлов — норма.

### Привязка подписи (ответ на вопрос ревью)

Второй ключ декоративен без трёх связей — вот они, конкретно:

1. **К пакету.** Каждый mirror-пакет получает `packet_id` (uuid) и `mirror_hash` (sha256 канонического текста пакета). Пакет уходит оператору вместе с `packet_id` в шапке.
2. **К оператору.** Доставка — только на allowlist chat_id; матрица Д5 получает запись `principal: <operator-chat-id> → role: ratifier`. Подпись со строки, не принадлежащей allowlist-принципалу — отбрасывается.
3. **К атомарному DEPLOY.** Подпись («утверждаю [packet_id]») → сервис: транзакция (записать статусы proposals → DEPLOY дистиллята → обновить граф → **receipt пишется ПОСЛЕ успеха всех записей**, с mirror_hash и principal). Любая ошибка внутри — полный откат, receipt не появляется, пакет остаётся pending.

Частичное отклонение («утверждаю кроме №3») → №3 в rejected с сохранением, остальные signed; без явного перечня — весь пакет pending.

### Порты алгоритмов HC (точные параметры)

- **Quote grounding:** нормализация (fold/lowercase), цитата ≥24 символов, ровно 1 вхождение в источнике; 0 или 2+ → запись отклоняется (fail-closed).
- **Идемпотентность двух классов:** FACT — UNIQUE(agent, category, key) + замещение только через supersede (никогда UPDATE); EPISODE — hash(content)+INSERT OR IGNORE.
- **Coverage recall-гейт:** θ=0.30 покрытия информативных слов, ≤5 фактов на ход, окно подавления повтора 6 ходов, колонка keywords у фактов.
- **Контестед-кластеры:** таблица entity_mentions + фильтры supersession; точность 30–50% приемлема (генератор proposals, человек решает).
- **SUPERSEDES в FTS:** фильтр WHERE, не множитель bm25 (sqlite.rs уже так и делает — совпало с нашей реализацией).
