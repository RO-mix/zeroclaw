# Анализ: пересборка PR #12201 под матрицу допуска 9-12

**Дата:** 2026-11-21. **Статус:** аналитический документ, кода нет.
**Вопрос:** заменить в открытом PR #12201 флаговую модель (`voice_without_mention`)
на матрицу допуска, отработанную в форке сторями 9-9…9-12 (эпик Channel Layering).

---

## 1. Короткий ответ

Да — это предложение апстриму нашего боевого решения. Форк остаётся пилотом,
PR — каналом вклада. Но вносить в ветку #12201 дельту эпика целиком (2307
строк в telegram.rs) нельзя: туда попали локальные порты патчей и инфра из
других PR. Ветку надо пересобрать с нуля на свежем мастере, вынеся **только**
ядро матрицы. Объём ядра — порядка 250–400 строк в одном файле, без изменений
конфига и API.

## 3. Чем матрица лучше флага (аргументация для апстрима)

1. **Ноль новых конфиг-ключей.** v1 добавлял `voice_without_mention` на канал
   (6 файлов: schema, orchestrator-резолверы, daemon, registry, src/config).
   Матрица использует существующий `passive_group_context` — семантика у
   оператора уже выучена: «группа прослушивается».
2. **Один инвариант вместо матрицы флагов.** «Каждое голосовое в
   прослушиваемой группе — текст в контексте». Упоминание управляет только
   ответом, не участием. Убирает класс багов «флаг × упоминание × тип медиа».
3. **Ровно одна точка решения.** Гейт — единственный источник допуска медиа;
   парсеры не несут своих правил (в форке это дисциплина 9-11, голосовой
   парсер прямо это задокументировал).
4. **Бритва Оккама по профилю репозитория** (anti-patterns AGENTS.md:
   «no speculative config/feature flags»). Флаг под один частный случай —
   именно тот паттерн, который гейт hygiene отсекает.

## 4. Варианты формы PR

### Вариант M (минимальный) — рекомендуется

Содержимое: один файл `crates/zeroclaw-channels/src/telegram.rs`:

1. `check_media_mention_gate` → возвращает `MediaAdmission`;
   `participation_decision` как чистая функция матрицы (≈26 строк);
   reply-to-bot обход сохраняется (в апстриме он есть — оставить его ветку
   как есть, не портить наше `addressed_to_bot`, это материал отдельного PR).
2. Голосовой парсер: `Passive` → транскрибировать, отдать `ChannelMessage`
   с `passive_context: true`, не входить в voice-chats режим.
3. Потребители photo/document: `Passive` пока маппится в `SkipPermanent`
   с комментарием «uniform passive for remaining formats — follow-up»
   (честно, без притворства).
4. Тесты: матрица гейта (упоминание × passive × captionless), пассивный
   голосовой парсер.

Объём оценочно 250–400 строк. Конфиг, API, orchestrator — не трогаются.
B2-дегрейды и пассивные photo/document — отдельными follow-up PR поверх.

### Вариант F (полный эпик)

Вся дельта 9-9…9-12 (~1900 строк суммарно). Против: тащит инфру, не нужную
для вопроса PR; пересекается со всеми соседними voice-PR; ревью размажется
на месяц. Отклоняется.

### Вариант S (сначала слоистая модель, потом голос)

Отдельный «фундаментальный» PR с `MediaAdmission`+матрицей, затем #12201
сжимается до голосовой ветки. Против: два ревью вместо одного, а польза
матрицы без единственного реального потребителя (голоса) неочевидна
ревьюерам. Апстрим не любит абстракции без потребителя (anti-pattern:
«speculative generality»). Отклоняется, но остаётся запасным, если tidux
потребует разделения.

## 7. Риски

1. **Смена дизайна посередине ревью.** tidux ревьюил v1 и просил только
   ребейз. Митигация: комментарий в PR «why the flag is gone» с четырьмя
   пунктами из раздела 3; ссылка на боевую эксплуатацию форка. Риск
   остаточный: ревью по существу начинается заново. Принимаем — честнее,
   чем протаскивать флаг, в который мы сами больше не верим.
2. **Половинчатость M (photo/document остаются Drop).** Ревьюер может
   спросить «почему не uniform». Ответ в PR заранее: пассивная запись
   photo/document требует сохранения файла (attachment core, 9-10) — это
   отдельный PR; здесь — только то, что не несёт новой инфры.
3. **Тестовый контур.** Матрица гейта и пассивный голосовой парсер должны
   покрываться юнит-тестами в самом PR (в форке таких тестов написано
   достаточно — переносим адаптированные, не пишем с нуля).
4. **Расхождение форк/апстрим после вливания v2.** Форк тогда несёт B2 и
   пассивные photo/document поверх того же гейта — дельта форка станет
   меньше на объём v2. Синхронизация — штатный процесс контура.
